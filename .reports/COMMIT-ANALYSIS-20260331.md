## 三、错误二：Commit 质量极差

### 3.1 模糊 commit 信息 — 69 / 335（21%）

超过五分之一的 commit 信息无法从中得知做了什么。典型例子：

```
fix: 修复一些问题
fix: 修复一些内容
chore: 修复一些问题
fix: 修复一些小问题
feat: 优化一些内容
```

这些 commit 半年后回头看，**完全无法判断改了什么、为什么改**。任何需要 `git bisect` 的场景下，这些信息等于没有。

### 3.2 feat 前缀滥用 — 10 次

以下 commit 用 `feat:` 但实际是 bug 修复：

```
feat: 修复 npm 发布的时候一些问题
feat: 修复打包的时候无法正常加载组件
feat: 修复 Tree 的拖拽问题
feat: 修复 crustify 的一些错误信息
feat: 修复代码的一些问题
```

**`feat` 意味着新功能。修 bug 是 `fix`。** 这导致 CHANGELOG 生成时新功能和 bug 修复混在一起，语义完全错乱。

### 3.3 无前缀 commit — 5 次

```
提交 pnp 的内容
修复 table 在 left 固定列的时候存在一些问题
Create jest.yml
```

连 Conventional Commits 的基本格式都没遵守。

### 3.4 重复 commit

```
2025-05-07  feat: 添加 rc-live       ← 同一天提交了两次完全相同的 message
2025-05-07  feat: 添加 rc-live
2025-01-03  feat: 添加缓存文件, 提高 CI 的部署效率   ← 也是同一天重复
2025-01-03  feat: 添加缓存文件, 提高 CI 的部署效率
```

## 十三、接下来应该做什么

### 阶段零：立即执行 — 安装 commitlint + husky（4 月 1 日，半天）

在写任何组件之前，**先堵住 commit 质量的漏洞**。这是成本最低、收益最高的一件事。

```bash
# 1. 安装依赖
yarn add -D @commitlint/cli @commitlint/config-conventional husky

# 2. 初始化 husky
yarn husky init

# 3. 添加 commit-msg hook
echo 'yarn commitlint --edit "$1"' > .husky/commit-msg

# 4. 创建 commitlint 配置
```

commitlint.config.mjs:
```js
export default {
    extends: ['@commitlint/config-conventional'],
    rules: {
        // 禁止模糊描述
        'subject-min-length': [2, 'always', 10],
        // scope 建议但不强制
        'scope-empty': [1, 'never'],
    },
};
```

**验收标准：** 尝试 `git commit -m "fix: 修复一些问题"` 必须被拦截（subject 太短或太模糊）。从此刻起，每个 commit 都被强制校验格式。

### 工作纪律

针对报告中暴露的问题，以下是必须遵守的规则：

1. **每周至少 4 天有 commit。** 间断不超过 3 天。设日历提醒。
2. **周末至少投入半天。** 这是唯一的整块时间。
3. **commit 信息必须具体。** 禁止"修复一些问题"。至少说明改了哪个文件/函数/行为。安装 commitlint 强制校验。
4. **不开新坑。** 在 P0 + P1 全部交付之前，禁止添加任何和组件库无关的功能。
5. **先写测试再写组件。** 至少写 3~5 个核心用例的测试骨架，再填充实现。
6. **CI 本地先验证。** `yarn test && yarn eslint` 全部通过后再 push。
