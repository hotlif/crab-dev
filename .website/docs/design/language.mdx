# 概览与设计原则

> **定位：Crab v1 设计提案。** 面向企业后台和专业工具。规范用于指导设计与验收；带“已实现”的规则已用于设计样板，带“迁移建议”的规则仍需在具体组件中逐项落地。

## 这套语言解决什么问题

后台产品的复杂性主要来自数据、权限、流程和状态。视觉语言首先要帮助用户识别正在处理的对象、找到下一步操作，并判断操作结果。基准紫色承担行动指引，中性色承载长时间阅读；稳定的布局与克制的反馈减少反复寻找信息的成本。

本规范参考 Material 3 将基础规则、视觉样式、组件用法和实现令牌关联起来的方法。色彩角色与前景配对的组织方式可参阅 [Material Web 色彩文档](https://material-web.dev/theming/color/)，组件规范的“类型、用法、无障碍、主题”结构可参阅 [Material Web 按钮文档](https://material-web.dev/components/button/)。文档站和设计样板采用 Material Web v0.192 基准色板；Crab 的尺寸、密度、布局与业务场景仍由本项目定义。配色映射见[色彩与主题](/design/color)，不代表公共组件库已迁移或所有参数均为 Material 3 默认规格。

## 四条设计原则

### 内容优先

页面标题说明当前对象或任务，正文回答用户需要知道的事实。装饰不能抢走主要数据与操作的注意力。同一个信息不应同时被大字号、鲜艳背景、厚边框和阴影重复强调。

例如，项目列表应首先呈现名称、状态与负责人；大面积品牌色背景不会让列表更容易比较。指标卡必须标明统计范围与时间，不能用突出的数字掩盖含义缺失。

### 层次清晰

用空间表示归属，用表面表示层级，用文字表示关系。相关控件靠近，独立任务分组留白；当前栏目、页内视图和对象状态必须有各自的表达方式。

顶部导航用于切换栏目，左侧目录用于栏目内部选页，页内目录用于跳转段落。三者不能都叫“分类”，也不能在同一位置承担互相冲突的切换行为。

### 操作精确

标签必须能预测结果。用户应分辨“保存当前修改”“提交审批”和“发布到线上”的不同后果。控件边界、焦点环、选中标记与禁用原因共同解释可操作范围。

每一个可发现的操作都应有可用的键盘路径。高密度不意味着缩小触控目标；批量操作必须先说明作用范围，再允许确认。

### 反馈克制

反馈靠近触发它的对象。字段错误留在字段附近，保存成功留在表单摘要附近，只有需要立即决策的情形才使用确认框。动效用于说明变化，不延迟用户继续操作。

失败时保留输入和工作上下文，说明下一步可执行的动作。不要让用户仅凭一次消失的消息判断保存是否完成。

## 规则等级与取舍顺序

| 等级 | 本规范中的含义 | 发生冲突时如何处理 |
| --- | --- | --- |
| 必须 | 影响可用性、数据理解或操作安全的要求 | 不能以美观或空间不足为由省略 |
| 应 | 默认推荐；确有业务理由时可调整 | 在设计说明中记录原因和替代方案 |
| 可 | 可选的增强能力 | 不应成为完成核心任务的前提 |

取舍顺序为：任务正确性、可访问性、信息清晰度、体系一致性、视觉表现。已有公共组件 API 与用户数据兼容性同样是约束，不能以统一视觉为由悄悄改变行为。

## 页面设计与评审流程

1. 写清用户、任务、入口、成功结果和失败后的恢复路径。
2. 列出对象、字段、统计口径、操作范围与权限边界，再安排信息顺序。
3. 选择布局、密度和主操作，使用现有视觉角色与组件变体。
4. 补全加载、空数据、错误、长文本、窄屏、键盘及暗黑模式。
5. 将设计稿上的数值映射到令牌；新增数值标为候选，不直接散落到组件中。
6. 用可重复的模拟场景验收，记录哪些已实现、哪些仍待迁移。

## 范围与后续演进

本规范覆盖设计规则、既有交互样板及公共组件的持续质量审查。当前工作包括紫色公共默认品牌、逐批组件修复和规范同步；完成情况以验证记录为准。动态取色、Logo 重设计和站点发布不在本轮范围内。新业务如果需要新的色彩或形状，先说明现有角色为何无法表达，而不是直接增加一套局部样式。

## 从任务到设计决定

### 先描述任务，而后绘制页面

设计说明必须包含角色、对象、入口、操作范围、成功结果和恢复方式。角色不是抽象的“用户”，而是具有具体权限和工作频率的人。项目管理员每天核对项目与偶尔查看进度的成员，可能使用相同数据，却不需要相同的默认操作密度。

| 典型任务 | 用户需要判断 | 页面首先提供 | 不应优先呈现 |
| --- | --- | --- | --- |
| 查找项目 | 查的是全部项目还是当前筛选结果 | 搜索范围、已用条件、结果数 | 没有统计范围的大数字 |
| 核对预算 | 单位、周期、缺失值是否一致 | 列标题、右对齐数值、完整值入口 | 与比较无关的大图标 |
| 批量处理 | 影响哪些对象、是否可恢复 | 选择摘要、数量、风险与确认 | 未选记录时可执行的删除入口 |
| 编辑成员 | 什么已保存、什么仍是草稿 | 常驻标签、字段分组、保存和取消 | 每个字段一张装饰卡片 |
| 修复失败 | 是否丢失输入、如何继续 | 原内容、失败范围、可执行恢复动作 | 只有错误码的全屏提示 |

项目台账和成员编辑贯穿本规范。样板提供已有流程的观察入口；表中批量处理等尚未实现的流程属于设计要求，不应从文字反推样板已有对应按钮。

### 五项交互原则如何落实

| 原则 | 必须回答的问题 | 项目台账 | 成员编辑 |
| --- | --- | --- | --- |
| 示能 | 用户如何发现可以操作 | 搜索像输入、排序像操作、静态指标不显示手形 | 字段有输入边界，编辑入口有动作名称 |
| 意符 | 当前能力与状态如何被感知 | 选择标记与范围文字共同出现 | 必填、错误、保存中有文字线索 |
| 映射 | 操作和结果是否自然对应 | 筛选位于受影响表格前，分页靠近结果 | 标签跟随字段，错误就近，保存回写摘要 |
| 反馈 | 操作是否已被接受 | 查询忙碌、结果计数和失败恢复清楚 | 提交立即反馈，成功后显示保存值 |
| 限制 | 如何阻止可预见的错误 | 不对未知范围执行批量操作 | 不重复提交，不静默丢弃草稿 |

四条设计原则定义方向，五项交互原则用于逐个检查可操作元素。一个外观整齐的页面若不能说明作用范围，仍不能通过评审。

## 读者如何使用规范

- 设计师：先用任务表确定结构，再从视觉基础选角色与参数，最后补齐状态和失败路径。交付稿必须同时说明默认态以外的行为。
- 开发者：先确认现有组件和数据契约，再核对规则对应的作用域。公共组件未提供的能力记录为差距，不用临时属性或隐式样式覆盖冒充已有能力。
- 评审者：按真实操作路径检查信息、反馈和恢复，再检查参数一致性。静态截图能证明排版，不能证明键盘、提交或权限行为。

建议把每个页面的设计记录压缩成一份可复核的任务卡：对象与角色、入口与返回位置、操作范围、布局与密度、状态清单、令牌来源、差距及验证记录。复杂页面可有多张任务卡，但同一主操作只归属一个明确任务。

## 规则等级与落实状态分开记录

“必须 / 应 / 可”表示规则强度；“现有实现 / 设计要求 / 候选规格 / 待落实差距”表示证据与进展。两者不能混成一个等级列表。例如：“触控目标必须满足 Crab 44px 约定”是设计要求；“某个按钮已满足”需要该按钮实际尺寸和设备验证作为证据。

| 落实状态 | 记录内容 | 不能据此推导的结论 |
| --- | --- | --- |
| 现有实现 | 来源、作用域、实际行为；验证范围另列 | 所有组件和设备已经符合 |
| 设计要求 | 目标、适用条件、可观察的通过标准 | 当前演示一定具备该行为 |
| 候选规格 | 参数、用途、现有引用与未来归属 | 公共令牌或 API 已稳定发布 |
| 待落实差距 | 当前表现、目标表现、影响与后续验收 | 本次文档更新已经修复组件 |

发生冲突时先保护任务正确性与可访问性，再选择能复用的既有能力。例如紧凑密度与触控命中区冲突时保留触控目标；统一视觉与公共 API 兼容冲突时登记迁移项；帮助说明与有限高度冲突时增加内容空间，不裁掉错误文字。

## 一次完整评审的输入与输出

1. 输入真实内容样本：正常、最长合理文本、未知值、零值、无权限和请求失败。不要只用等长占位文字。
2. 指定默认任务和主操作，说明为何使用表格、抽屉或普通页面；不能仅引用“风格统一”作为选型理由。
3. 对照色彩、尺寸、状态和焦点的权威章节；重复规则以链接引用，避免局部另写一套参数。
4. 从进入到完成走完主流程，再走取消、失败、重试和失去访问资格的流程。
5. 输出已通过项、阻塞项及候选规格。对无法实测的辅助技术或设备写明待验收，不用“理论支持”代替结果。

**正例**：台账明确“当前页已选 3 项”，确认内容重复对象数量，完成后更新结果；取消后选择仍然可见。**反例**：工具栏只有“操作成功”，没有说明影响哪些记录，刷新后用户才发现范围错误。修正应先明确作用范围与结果，而后调整颜色和位置。

交付时，任意一个可见操作都应能回答“谁能执行、影响什么、何时完成、失败怎么办”；任意一个规范数值都应能找到来源或候选说明。
