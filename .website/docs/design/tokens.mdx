# 令牌与实施

设计令牌把视觉决策映射为可维护的实现。规范先定义语义，再选择数值；同一个“主要操作”角色应在不同组件与主题下保持一致，不能让每个页面自行挑选相近的紫色。

## 三层令牌模型

| 层级 | 职责 | 示例 | 修改影响 |
| --- | --- | --- | --- |
| L1 全局基元 | 提供原始色阶、空间、字号等基础值 | 原始色阶、4px 空间基准 | 广泛影响引用它的上层角色 |
| L2 语义映射 | 说明值的用途与主题关系 | 主要操作、正文、表面、焦点、交互动效 | 跨组件共享设计意图，主题在此切换 |
| L3 组件令牌 | 表达特定组件的局部结构与状态 | 按钮高度、表格行高、浮层圆角 | 限于组件能力和局部表现 |

源定义优先引用上一层，减少重复的字面值。颜色使用 OKLCh；主题切换覆盖语义变量，不在组件逻辑里散落浅色与深色分支。生成的令牌文件是构建产物，不能手工编辑。

### 参数管理位置

原始色板在公共 L1 token.toml，明暗配对集中在 rc-token-semantic/src/theme.ts，由 rc-theme 编译 CSS。docs/site/palette.ts 提供站点展示别名，paletteStyles.ts 仅绑定站点专用变量，不重复覆盖公共 L2。尺寸、密度与排版继续集中于 docs/site/design/tokens.ts，样板 styles.ts 只负责结构和局部尺寸；正文使用手写 MDX，目录由 navigation.toml 管理。章节中的描述应与集中参数保持一致，修改时同时检查相关文档和样板。

这里的 tokens.ts 是手写的展示参数模块，与组件包内由 token.toml 生成的 src/token.ts 不同。前者可以随样板维护，后者只能通过令牌生成命令刷新。

## 作用域与主题继承

设计语言页保留站点共用顶部与独立目录。正文、样板与顶部使用同一个主题状态，任一主题控制都会同步其他区域，并保留站点的系统偏好和刷新记忆。密度仅调整当前样板，进入新章节默认恢复标准。

文档根、站点浮层、样板根与样板浮层通过 data-theme 使用公共主题；样板继续覆盖必要 L3 尺寸变量，复用公开组件能力。独立 iframe 示例不继承文档站 CSS，应独立导入 rc-theme/css/index.css，公共默认 Light 品牌同样为紫色。Drawer、Dialog 及其他 Portal 内容必须同步主题与密度；不能假定 DOM 之外的浮层会自动继承样板变量。

深色主题必须重新校验前景与表面配对。品牌色变亮后，其上文字也可能需要换为深色；仅替换背景并不保证可读性。

## 静态样式与组件边界

- 使用 Crab CSS 静态样式块；模板插值必须在构建期可求值。
- 条件样式拆为静态块，再通过已有组合机制选择；不引入运行时内联样式。
- 优先引用现有令牌，只为尚无对应语义的决策登记候选参数。
- 复用 Button、Table、Form、LineEdit、Select、Card、Tag、Drawer、Dialog 等公开组件。
- 样板所需尺寸通过已有属性与变量表达，不增加公共 density Props。公共默认品牌本轮改为紫色，旧变量与属性保留；迁移须验证现有覆盖。
- 交互遵守 React 19 与编译器规则，状态、标签关联和异步提交由现有框架能力承接。

规范页面描述规则；组件文档描述具体 API。两者通过有意义的引用关联，不把组件 API 表复制成另一份需要同步维护的规范。

## 组件迁移顺序

| 阶段 | 建议对象 | 需要先确认的条件 |
| --- | --- | --- |
| 1 · 基础操作 | Button、LineEdit、Select、Tag | 品牌前景、必要边界、状态组合、两种密度 |
| 2 · 数据与容器 | Table、Card、Pagination、Empty | 行高、数值排版、查询范围、窄屏滚动 |
| 3 · 表单与浮层 | Form、Drawer、Dialog 及下拉容器 | 校验、Portal 继承、焦点约束与恢复 |
| 4 · 反馈和全库推广 | Alert、Spin 等其余组件 | 反馈等级、减少动态效果、强制颜色与兼容性 |

每一步先完成对照样板和回归验证，再考虑稳定化令牌或公共能力。迁移清单是下一阶段工作，不等于本轮已经改造全库。

## 修改与验证流程

1. 写明规则解决的任务，检查是否已有对应令牌或组件能力。
2. 在文档站与设计样板作用域内验证变化，更新中文规范与候选参数记录。
3. 对两个主题、两种密度和关键状态检查前景、表面、边界与焦点。
4. 验证键盘、320px / 768px / 1440px 布局、减少动态效果与强制颜色。
5. 涉及 token.toml 时运行 generate:token，由命令刷新产物；不得手改生成内容。
6. 运行受影响范围的 ESLint、类型检查、Wake 测试与生产构建，检查生成内容一致性和构建绑定。
7. 用生产预览复核交互和截图，记录已有失败、当前限制与后续迁移项。

正文至少 4.5:1，必要图标、控件边界与焦点至少 3:1。自动数值测试不能替代实际状态与布局检查；浏览器截图也不能证明读屏或完整 WCAG 合规。

## 版本与维护

规范从文档与样板建设进入公共主题和组件逐批验证阶段。规则变化需说明动机、影响的章节与组件，以及是否影响兼容性。设计数值、截图与实现不一致时，应先判断哪一方需要修正，不能单独更新截图掩盖行为差异。

本轮包含公共默认品牌统一与逐批组件审查，不包含 Logo 重设计、动态取色算法或站点发布。实施依据是已经验证的规则与公开能力，不是对 Material 3 外观或 API 的复制。

## 规则的唯一解释位置

| 规则 | 权威章节 | 其他章节的职责 |
| --- | --- | --- |
| 色彩角色、前景背景配对 | 色彩与主题 | 说明本任务使用哪个角色 |
| 字体、数字与长文本 | 字体与排版 | 给出具体数据样本 |
| 尺寸、密度、间距与重排 | 布局与密度 | 说明局部布局与例外 |
| 圆角、边界、阴影 | 表面、层级与形状 | 说明容器关系 |
| 状态组合与转换 | 状态系统 | 说明组件的触发和结果 |
| 焦点、标准等级与验收 | 无障碍与键盘 | 补充本组件的键盘差异 |
| 反馈时长与任务等待 | 反馈与等待 | 说明当前操作如何恢复 |

动效时长由动效章维护，等待时长由反馈章解释，两者不能互相替代。业务章可以重复必要的可执行步骤，但应链接共性规则，不再维护第三份色板或焦点参数。

## 候选规格的登记方法

每个候选包含：角色名称、解决的问题、值或范围、单位、现有来源、主题与密度适用条件、消费者、验证证据及兼容性影响。没有测试证据时写“待验证”，不能因为表格完整就改为稳定规范。

候选先尝试复用上一层语义。若只是某个样板的容器宽度，不应直接提升为全局令牌；若多个组件确实共享同一语义，再评审是否建立 L2。新增公共名称和移除旧名称都需要独立迁移决策，本次文档建设不做发布承诺。

单位必须清楚：控件高度用 CSS px，行高区分具体长度与倍数，时长区分 ms 与 s，透明度区分比例与百分比。颜色存储空间与状态混合空间分别记录，不将 OKLCh 原始值误解为所有混合也在 OKLCh 中完成。

## 当前差距与下一阶段验收

| 差距 | 影响 | 下一阶段通过条件 |
| --- | --- | --- |
| 公共默认已改为紫色，完整视觉复审未完成 | L3 局部覆盖与旧业务样式仍可能造成差异 | 逐包验证明暗、状态、Portal 和自定义覆盖 |
| 密度、排版仍以样板局部参数表达 | 无法声称所有组件统一密度 | 公共语义及组件消费一致，保留 API 兼容 |
| 图标基准未形成统一资源迁移 | 旧图形重量与尺寸可能不同 | 核对图形、名称、命中区与所有状态 |
| 模态动画部分在 JavaScript 中配置 | 通用 motion 不覆盖所有进退场 | 统一来源后验证中断、关闭与减少动画 |
| 工作台无排序、批量与网络数据 | 完整生产流程只能作为设计要求 | 真实范围、请求竞争与失败恢复验证通过 |
| 表单无全局离开保护与服务端冲突 | 本地成功不能代表生产可靠性 | 草稿、权限、冲突、结果未知有可恢复流程 |
| 字段计数与错误清除为样板策略 | 不能泛化所有语言和产品 | 产品计数契约与校验生命周期一致 |
| 辅助技术和设备未全覆盖 | 不能声明全库无障碍合规 | 记录真实设备、浏览器和完整任务结果 |

这些是持续质量审查中的待验收项，不是已修复的能力。组件级缺口需要按最小影响面分别实现和回归，不能为了让规范“看起来一致”修改演示说明掩盖问题。

## 变更评审与文档验收

规则改动先列出受影响角色与章节，核对当前源码，再更新权威章节和引用。设计要求与已有行为不同时两者都保留说明；确认源码错误时记录待落实差距，不能偷偷把错误行为改写为设计目标。

**正例**：发现 Drawer 进入为 300ms、退出为 200ms，动效章明确实际来源，令牌章记录统一待迁移。**反例**：文档一律写“使用 fade 200ms”，实际体验不同却没有解释。修正为可追溯映射，后续再评审实现。

纯文档变更运行 check:docs、test:generator 和 build，检查路由、MDX、链接与生产页面；组件或令牌变化则追加仓库要求的生成、ESLint、测试和构建。公共默认外观变化必须同步迁移说明；新增 themeColorContract 为公共配对数据入口，不替代 CSS 主题入口；不增加依赖。验收记录应同时列出通过项、已有失败和未测试范围。
