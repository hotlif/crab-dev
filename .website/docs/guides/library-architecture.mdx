# 组件库体系

Crab UI 是可按包使用的 React 组件库。设计令牌、配置和通用交互支撑基础组件，组合组件复用这些基础，专业能力与路由等集成按需选择。文档和工作台服务组件的使用与维护。

## 两个分类轴

能力族说明依赖职责和组合层级；用途分类说明开发者在界面中要完成的任务，两者独立。一个日期选择器可以属于组合组件，同时属于数据录入；Router 是可选集成，而非必须随按钮引入的基础依赖。

| 能力族 | ID | 边界 |
| --- | --- | --- |
| 基础支撑 | foundation | 全局/语义令牌、主题、配置、Hook 与测量能力 |
| 基础组件 | base | 独立控件、内容展示和交互基础 |
| 组合组件 | composite | 复用基础能力的字段、集合和布局 |
| 专业扩展 | extension | 复杂数据、图形与文档编辑 |
| 可选集成 | integration | 路由、远程模块等独立能力 |
| 开发支持 | devtool | 演示、预览和组件文档工具 |

用途包括设计基础、通用、数据录入、数据展示、导航、反馈、布局与工具。当前包和分类以产品清单为准；[组件目录](/learn/components)按能力族组织，并为每个包标注用途。

## 唯一产品清单

根目录 `library.manifest.json` 记录名称、路径、能力族、用途、生命周期与设计覆盖；各包 `package.json` 记录版本、依赖与导出。`scripts/library-manifest.mjs` 统一读取，文档生成器派生目录、导航、库存和覆盖矩阵，不固定包数或示例数。

运行时依赖应符合能力职责；组件示例使用其他包的依赖单独登记为文档角色。构建拓扑从生产源码和令牌引用生成，不通过人工删除必要 PnP 依赖消除表面上的环。

[包依赖图](/guides/dependencies)与完整邻接表由产品清单、包声明、实际生产/文档源码和令牌引用生成，可以分别查看生产、文档和令牌关系。它和 Turbo 使用相同检查来源，不另外维护手写依赖图。

生产源码及类型声明不能通过相对路径穿越包边界，也不能引用文档运行环境。跨包能力从已声明的公共入口取得；`check:architecture` 检查实际源码引用。

## 包内职责

保持现有发布包边界，在包内按修改原因组织模块。静态组件样式放在相邻的 `*.styles.ts`；渲染文件处理结构与事件，专属规则留在所属包。通用受控状态、字段关联与浮层协调放在 Hooks，配置与 CSS 边界放在 ConfigProvider。

| 能力 | 模型与规则 | 状态、资源与边界 | 渲染 |
| --- | --- | --- | --- |
| Table / TablePro | `types`、`util`、`valueAccess` 与排序、树、分组 Hook | 选择、编辑、拖动、列布局、测量与焦点 Hook | Table 编排视图；TablePro 通过 Table 的公开能力组合 |
| Form | `types`、`util`、`field-adapters` | `bus`、`hooks/useForm` 与字段上下文 | `form`、`item` 与相邻样式 |
| Tree | `type`、`util` | `hooks/useTreeData` | `tree`、`nodeItem` 与相邻样式 |
| Canvas / FlowDiagram | 形状、矩阵、路径与绘制协议；ELK 布局与连线路由 | 控制与路由 Hook、WebGL renderer、文字 atlas | Canvas 视口与形状；FlowDiagram 节点与边 |
| PdfEditor | `protocol`、`geometry`、`document-layout` | `engine`、`client`、`session`、Worker 与插件宿主 | 文档舞台、页面、面板、工具栏及 Web Component 适配 |
| Router / Realm | 路径匹配；加载协议与共享范围 | history 与导航；loader、importer 与 sandbox | Outlet、Link；Realm 与错误边界 |

渲染器、Worker、WASM 和远程资源的创建与释放由所属引擎或会话承担。测试从相应模块或包入口进入；文档站只消费这些能力。ComponentPreview 负责演示与源码展示，不成为专业引擎的依赖。

文档生成按读取、TypeScript 类型提取、页面渲染和产物写入分模块。包内 `docs/presentation.json` 定义展示布局与 Demo 分组，生成器不按组件名称维护另一套分支。根检查、包内检查与 CI 从 `scripts/check-plan.mjs` 组合真实公开脚本。

## 包生命周期

| 状态 | 含义 | 进入下一阶段的依据 |
| --- | --- | --- |
| experimental | 能力可试用，API 与设计仍可调整 | 公共类型、行为、示例、工程检查及适用设计状态完整验收 |
| stable | 公共契约有持续验证，可按版本规则升级 | 不兼容变更必须有版本说明和迁移路径 |
| deprecated | 已有替代方案，保留明确退出计划 | 说明替代包/API、影响和移除版本 |

生命周期与视觉覆盖是两件事。某个包运行通过，不能自动将三套设计都标为已验收；没有独立视觉的工具包仍需类型、行为和导出检查。实际状态见[覆盖矩阵](/guides/design-coverage)。

## 维护一项能力

先确定职责、所在能力族和既有可复用包，再确定公共 API、无障碍语义、设计变体与令牌。实现、测试、组件正文、独立示例和迁移说明同时完成。每项规则例外记录理由、作用范围、验证证据和退出条件；历史 review 不替代现行规范。
