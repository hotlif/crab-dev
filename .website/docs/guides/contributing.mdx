# 贡献与维护

从产品职责与影响面出发，一次变更同步公共类型、运行行为、设计令牌、示例、测试和迁移说明。规则入口是根 AGENTS，组件和文档子目录补充适用规则。

## 来源与生成

任务开始时，从仓库根运行 `yarn ai:context <包名或仓库相对路径>`。默认目标 `.` 返回全局导航；`--json` 提供结构化结果，`--dependents` 补充直接使用方。输出只包含路径、用途和命令，不读取全部规范正文，不运行生成或验证，也不保存上下文快照。文件路径统一相对仓库根，未知目标报错。

先读目标目录继承的 AGENTS，再按实际任务读取指南和技能。关联来源的规则单独列出，仅在编辑这些来源时适用。专项规则就近维护在有独有约束的包内，通用契约保留在指南；能力族通过产品清单表达，不另建物理目录分类。

下表的命令在仓库根运行；`<包名>` 替换为真实 workspace 名。精确脚本以查询结果和各工作区 `package.json` 为准，生成物必须通过对应脚本刷新。

| 内容类型 | 编辑来源 | 生成物或发布位置 | 生成与验证入口 |
| --- | --- | --- | --- |
| 产品信息、分类、生命周期、覆盖及设计身份 | `library.manifest.json` | 公共设计 registry、选择器、库目录、导航、覆盖矩阵、README 库存区域 | `yarn generate:architecture`、站点 `generate:docs`、`yarn check:architecture` |
| 版本、依赖、导出 | 各包 `package.json`，版本由 Changesets 更新 | PnP 运行时、lockfile、发布入口 | `yarn install --immutable`、`yarn build:library`、`yarn check:exports`、`yarn check:consumer` |
| 运行时拓扑 | 包声明、生产源码、令牌引用 | `turbo.json`、站点依赖图 | `yarn generate:architecture`、`yarn check:architecture`、站点 `generate:docs` |
| 设计令牌 | 各包 `token.toml` 与包内生成器 | `src/token.ts` 及包声明的额外生成物 | `yarn workspace <包名> generate:token`、`yarn check:tokens`、包内 `check` |
| 组件正文、交互 Demo、API | 包内 `docs/index.mdx`、`docs/demos/`、真实类型 | `public/docgen.json`、站点组件页与 API 数据 | 包内 `generate:docgen`（若提供）、站点文档验证 |
| 教学文字与 FAQ | `.website/content/` | 教程模块、学习页与检索文字 | 站点文档验证 |
| 组件预览布局、密度、分组与顶部 Demo | 各包 `docs/presentation.json` | 组件示例记录与预览索引 | 站点文档验证 |
| 教学步骤运行文件 | `.website/docs/examples/` | 从运行文件提取的教程源码与预览 | 站点文档验证，运行代码另跑站点 `lint`、`typecheck`、`test` |
| 维护与设计规范 | `.website/docs/guides/` 中非生成正文 | 原路径发布 | 站点文档验证 |
| 站点布局、预览桥接 | `.website/docs/site/` | 站点构建产物 | 站点 `check`，界面变化另做浏览器验收 |
| 工程工具与 AI 查询 | `scripts/` | 不生成持久化上下文 | `yarn lint:tools`、`yarn check:architecture` |

“站点文档验证”指 `yarn workspace @crab-dev/website generate:docs`、`check:docs`、`test:generator` 及根 `yarn docs:build`；后三项分别通过同一 workspace 或根脚本执行。

组件 Demo 用于工作台中的组件行为展示；教学步骤文件面向独立复制运行，由教学 JSON 的步骤关联，二者各有职责。查询生成文件会返回编辑来源；缓存、构建目录和历史资料不进入默认源码入口，仍可显式查询。混合文件如 README 仅库存区域生成，其他正文仍直接维护。

令牌、docgen、聚合页面、导航、目录、覆盖矩阵和库存通过对应生成器产生。生成器检查清单覆盖、唯一 ID、来源关联和漂移；不要通过固定包数阻止合理新增能力。

## 验证契约

根 `yarn check` 和包内 `check` 从 `scripts/check-plan.mjs` 读取检查计划。`yarn check --list` 只列出根阶段；CI 的 Test 工作流在 Windows 与 Linux 各执行同一个入口，原有 test、lint、typecheck 状态复用完整结果。发布仍等待同一提交的完整 Test 工作流成功。

浏览器 CSS 统一通过 `scripts/published-styles.mjs` 收集真实产物，按依赖顺序去重；声明了 CSS 导出却缺少文件时直接失败。包内保留夹具、特有准备与断言，避免各自维护依赖遍历和缺失产物策略。

包内额外生成产物通过 `package.json#crab.generatedArtifacts` 按实际任务登记。`build:library` 可登记包内正向输出模式，例如 `public/runtime/**`；拓扑生成器将其纳入缓存恢复并排除于输入，避免冷工作树命中缓存后缺少 Worker、WASM 或 Web Component 资源。不要在中央生成器维护组件名称分支。

Turbo 保持严格环境模式，仅透传构建线程、临时目录与浏览器定位参数；在父进程设置这些参数，不代表它们已进入严格模式子任务。行为与浏览器测试每次实际执行，构建和生成物继续复用缓存，避免跨运行环境借用旧测试结果。

视觉来源指纹也包含包内原始 `public/` 资源，如远程入口、字体和样本；`public/docgen.json` 与按 `generatedArtifacts` 声明的运行时复制产物分别按生成规则处理，避免把生成副本当成第二份来源。

| 影响 | 最小验证 |
| --- | --- |
| 组件源码 | lint、typecheck、包内 test |
| 令牌或消费方式 | generate:token、令牌契约及源码检查 |
| 导出、构建或 Wake 配置 | build:library、test 与消费方类型检查 |
| 文档来源或生成器 | generate:docs、check:docs、test:generator |
| 站点运行界面 | 站点 lint/typecheck/test/build，实际浏览器状态与布局验收 |
| 全库公共 API 或产品规则 | 统一验证入口，全部受影响包与同一提交的 CI 结果 |

工程结果、浏览器自动测量和人工复审分别记录。库内 DOM 测试没有布局引擎；触控、窄屏、键盘焦点、强制颜色、减少动画和设计差异按实际影响另验。

### 浏览器检查

统一检查执行包内登记的浏览器行为和无障碍回归；全库截图基线回归不作为发布门禁。安装所需 Chromium：`yarn test:browser:install`。

必须持续执行的附加测试由包的 `package.json#crab.requiredChecks` 登记已有 `test:*` 脚本。包内 `yarn check`、根 `yarn test:required`、根统一 check 和 CI 会执行登记项；交付前不能仅凭默认 `yarn test` 通过省略这些检查。登记须为无重复的数组，脚本必须存在且以 `test:` 开头；仅需显式运行的其他 browser 测试不会因此自动变为全库必跑项。

登记范围与入口由包元数据派生，可用根 `yarn test:required --list` 查看；维护时检查已有独立测试是否属于持续必跑范围，不能用文档内固定清单替代元数据。网站默认测试另包含构建后绑定检查器的正反契约，实际生产产物扫描仍由构建入口执行。

## 例外

例外说明规则来源、必要原因、影响范围、兼容风险、验证和退出条件。编译器手动引用稳定、第三方 PnP 补充、文档依赖、紧凑规格和无对应官方组件的扩展都适用。例外不能只藏在审查日志或全局忽略中。

工具兼容适配遵循同一要求。当前 Wake 的公开函数默认参数与默认泛型声明限制见[工具链](/guides/toolchain)，以实际发行声明和独立消费验证决定范围；不扩大为全库内部代码的禁令。

## 生命周期与发布

每项公开变更提供 Changeset，说明用户可观察行为和迁移要求。Changesets 自动准备版本与 Release PR；相同提交通过验证后才由 CI 发布。禁止手工升版建立第二流程或本地 publish。提交使用英文 Conventional Commits，生成文件与来源同次提交。

当前流程使用 GitHub 自带 token 创建或更新版本 PR，维护者需要在该 PR 的检查区域点击 **Approve workflows to run**，让等待批准的验证开始运行，具体行为见 [GitHub 工作流触发规则](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)。发布守卫同时核对成功验证的提交、实际检出的 HEAD 和 GitHub Action 使用的 SHA；版本 PR 验证与合并后的发布验证分别保留，不能用较早提交的通过结果替代。

experimental / stable / deprecated 和设计覆盖分别维护。只有对应证据完备，才能将包升级为 stable 或某体系标为 verified。

## 覆盖记录

设计覆盖根据实际核对范围记录；未验收的范围保持 partial。临时浏览器缓存和构建产物不作为源码提交。

验收分别记录“规范已起草、API 已迁移、工程已通过、视觉交互已核对”四层，各自保留范围和未验项，不能相互替代。设计矩阵包含明暗、尺寸、密度、方向、语言和状态六个轴；提升 verified 时还须满足工程守卫要求的精确源码、产物指纹和实际证据路径。
